## 1. Co powstało (od zera do działającej aplikacji)

W ciągu sesji zbudowaliśmy **działające narzędzie webowe** do analizy wyników EwE/Ecosim:
od pustego repo (tylko `.venv` + dane) do pełnego pipeline'u **ingestia → store → API →
frontend** z multi-wyborem zmiennych i koszykiem gotowym dla skryptów R.

Architektura wg zasady **„surowe → kanoniczne → prezentacja"**: warstwa ingestii raz parsuje
cały bałagan Ecosim do kanonicznego store (Parquet + DuckDB), a API, frontend i przyszłe
skrypty R pracują wyłącznie na tym modelu.

## 2. Backend (Python, FastAPI) — zrobione

- **Parsery** (`backend/ecosim/ingestion/parsers/`):
  - `ecosim_csv.py` — obsługuje 4 kształty CSV (szeroki-wg-ID, szeroki-wg-nazw, długi
    flota-grupa, jednoseryjny), zdejmuje blok `<HEADER>`, miesięczne timestepy → daty;
    zwektoryzowany (`melt`/`map`, ~60 s na komplet). Konsolidacja `predation_*` i `prey_*`
    w pojedyncze zmienne `predation` / `prey`. Lekki czytnik nagłówka `read_header()`.
  - `group_map.py` — `Mapa_grupy_fleets.xlsx` → 50 grup + 9 flot (ID↔nazwa).
  - `trend_csv.py` — `trend_*.csv` (drivery input) → tidy.
- **Kanoniczny schemat** (`core/schema.py`) — jedna tidy tabela (scenario, domain, variable,
  freq, date, year, month, group_*, fleet_*, partner_*, value, unit).
- **Zapis Parquet** (`ingestion/store.py`) — partycje `scenario=/domain=/variable=/freq=`.
- **Pipeline** (`ingestion/pipeline.py`) — odkrywanie scenariuszy, ingestia per-scenariusz,
  eksport słowników, przebudowa katalogu. **Nazwa scenariusza brana z nagłówka
  `EcosimScenario`** (autorytatywna), nie z nazwy folderu.
- **Katalog DuckDB** (`catalog/build.py`, `categories.py`, `service.py`) — tabela
  `catalog_datasets` z `category` (7 kategorii Results Extractor), widok `timeseries`,
  tabele wymiarów. Zapytania read-only dla API.
- **API** (`api/`): `/health`, `/catalog/scenarios|tree|datasets` (z `category`, `label`),
  `/dictionaries/groups|fleets`, `/timeseries`, **`POST /admin/reload`** (Reload Data).
- **CLI** (`cli.py`): `ecosim ingest | catalog | serve`.
- **Testy** (`tests/`) — 7 testów parsera (4 kształty + predation + prey), 7/7 OK.

**Dane po ingestii:** 668 plików → **7,8 mln wierszy, 146 datasetów, 5 scenariuszy**
(`Baltic_Ecosim`, `baseline cumulative`, `HAS_Cumulative` — output; `BAU`, `HAS` — input).

## 3. Frontend (React + Vite + TS) — zrobione

- **Katalog** (`features/catalog/`): przeglądarka zmiennych z **poziomem 0 = Rok/Miesiąc**,
  **rozwijanymi sekcjami kategorii** (domyślnie zwinięte), filtrem tekstowym i **multi-wyborem
  (checkboxy)** zmiennych z różnych kategorii. Kategorie = 7 grup Results Extractor; puste
  ukryte; drivery w osobnej sekcji.
- **Panel analizy** (`features/timeseries/`): `AnalysisView` + `VariableChart`:
  - **wspólne kontrolki** (Scenarios / Groups / Fleets jako rozwijane dropdowny / Year range)
    sterujące wszystkimi wykresami,
  - **koszyk = manifest dla R** (chipy wybranych zmiennych, „Copy manifest (JSON)", „Clear all"),
  - **siatka wykresów** — po jednym wykresie porównawczym na zmienną (Recharts), filtr
    grup/flot stosowany tylko tam, gdzie zmienna ma dany wymiar.
- **Nagłówek**: przycisk **„Reload Data"** (uruchamia ingestię w procesie serwera i odświeża
  katalog), licznik zmiennych, nazwy scenariuszy z `EcosimScenario`.
- **Proxy** Vite `/api` → backend :8000 (bez CORS).

## 4. Kluczowe decyzje projektowe

- **Cały interfejs po angielsku** (twarda reguła; dokumentacja/komentarze mogą być po polsku).
- **Lokalnie najpierw, architektura gotowa na serwer.** Stack: FastAPI + React.
- **Nazwy scenariuszy = `EcosimScenario` z nagłówka CSV** (obowiązujące).
- **Konsolidacja `predation`/`prey`** zamiast 45 osobnych pozycji.
- **Kategorie** liczone regułą (wymiarowość + nazwa) — jedno źródło prawdy (`categories.py`).
- **Multi-wybór zmiennych** + wspólne kontrolki + koszyk = manifest (kontrakt R z
  `docs/data-contract.md`).
- Usunięto przełącznik „Relative to base year (%)" — tego typu przekształcenia robimy w R.

## 5. Środowisko (ważne dla kolejnych sesji)

Maszyna za firmowym CA/proxy — domyślne instalatory wiszą na TLS:
- **Python:** `uv pip install --native-tls <pakiety>` (po ustawieniu `$env:VIRTUAL_ENV`).
  Zainstalowane: pandas **3.0.3**, pyarrow 24, duckdb, fastapi, uvicorn, typer, openpyxl.
- **Node/npm:** `$env:NODE_OPTIONS="--use-system-ca"` przed `npm install`/`npm run dev`.

Uruchomienie (dwa terminale):
```powershell
# backend
$env:PYTHONPATH="backend"; .\.venv\Scripts\python.exe -m ecosim.cli serve --port 8000
# frontend
cd frontend; $env:NODE_OPTIONS="--use-system-ca"; npm run dev   # http://localhost:5173
```

## 7. Czego jeszcze NIE ma (następne kroki)

- **Moduł przestrzenny `.asc`** (Etap 2): parser ESRI grid → COG + indeks rastrów, API
  `/spatial`, mapa z suwakiem czasu. (Obecnie ingestowane są tylko CSV + trendy driverów.)
- **Framework R** (Etap 3): runner (sandbox `manifest.json` + dane → `Rscript` → `out/result.json`),
  pakiet `ecosimkit` (jest szkielet w `rkit/`), UI uruchamiania analiz + renderery wyników.
  Koszyk w `AnalysisView` już produkuje manifest — to wejście dla runnera.
- **Eksport** wykresów (PNG) / danych (CSV) z poziomu UI.
- **Reload**: obecnie nadpisanie „w miejscu" — usunięcie scenariusza z `DataEcosim/` nie kasuje
  go ze store (do rozważenia pełne czyszczenie przy reloadzie); dla dużych danych — reload w tle.
- **Hardening na serwer** (Etap 4): auth, kolejka zadań, konteneryzacja R.
