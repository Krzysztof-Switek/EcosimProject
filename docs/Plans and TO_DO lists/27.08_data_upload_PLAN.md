## 1. Jak dziś działa ładowanie danych (punkt wyjścia)

- `backend/ecosim/core/config.py`: `Settings.raw_dir` ma wartość domyślną
  `<project_root>/DataEcosim`, nadpisywalną **jedną** zmienną środowiskową
  (`ECOSIM_RAW_DIR`), czytaną **raz przy starcie procesu** i buforowaną na stałe
  (`@lru_cache def get_settings()`).
- `POST /admin/reload` (`backend/ecosim/api/routers/admin.py`) i przycisk "Reload Data" w
  górnym pasku (`App.tsx`) każą od nowa przeskanować **ten sam, sztywny** `raw_dir` — nie ma
  sposobu, żeby wskazać inny katalog bez zmiany zmiennej środowiskowej i restartu serwera.
- Ekran startowy (`Landing.tsx`) od razu pokazuje 3 kafelki (Spatial/Timeseries/Monte Carlo)
  — nie pyta w ogóle, skąd wziąć dane.
- **Dobra wiadomość znaleziona przy przeglądzie kodu**: prawie każda funkcja w backendzie
  (`ingestion/pipeline.py`, `ingestion/spatial_pipeline.py`, `catalog/service.py`,
  `catalog/build.py`, `analyses/runner.py`, `analyses/registry.py`) **już przyjmuje
  `settings: Settings | None = None`** jako parametr i tylko *domyślnie* woła
  `get_settings()`. To znaczy, że przebudowa jest dużo mniejsza, niż mogłoby się wydawać:
  wystarczy zmienić, **co zwraca `get_settings()`**, żeby cała reszta systemu automatycznie
  zaczęła działać na wybranym źródle — bez przepisywania logiki ingestii/katalogu/analiz.

## 2. Decyzja projektowa: jeden mechanizm dla trybu lokalnego i serwerowego

Kluczowe założenie (do potwierdzenia z użytkownikiem — patrz sekcja 8, pytanie 1): "wrzucanie
danych na share" oznacza **sieciowy katalog zamontowany w systemie plików serwera**
(SMB/NFS/dysk sieciowy), a nie upload pliku przez przeglądarkę. To ważne, bo pojedyncza
paczka danych to ~28 GB — przesyłanie tego przez `<input type="file">`/HTTP POST byłoby
niepraktyczne, a przeglądarka i tak nie potrafi przekazać serwerowi "prawdziwej" ścieżki w
jego systemie plików (webowe API plików daje tylko zawartość, nie ścieżkę). Skoro dane i tak
muszą fizycznie wylądować w miejscu, które **backend widzi jako zwykły folder**, to zarówno:

- **dziś (dev/lokalnie)** — folder na dysku dewelopera, oraz
- **docelowo (serwer)** — podfolder na zamontowanym udostępnionym katalogu sieciowym,

to **ten sam przypadek z punktu widzenia backendu**: "wskaż ścieżkę, którą mogę czytać".
Budujemy więc **jeden mechanizm wyboru/rejestracji katalogu źródłowego**, używany
identycznie w obu trybach — różni się tylko to, co jest zamontowane pod spodem, nie kod.

## 3. Nowy komponent: rejestr źródeł danych (`WorkspaceRegistry`)

### 3.1 Dlaczego rejestr, a nie tylko "podaj ścieżkę i zapomnij"

Użytkownik będzie miał więcej niż jedną paczkę danych w czasie (dokładnie jak dziś — "mam
nową paczkę danych"). Zamiast wymuszać pełne przeładowanie za każdym razem, gdy ktoś chce
wrócić do poprzedniego zestawu, aplikacja **pamięta wszystkie znane źródła** i pozwala
przełączać się między nimi błyskawicznie (patrz 3.3 — każde źródło ma **własny** kanoniczny
magazyn, więc przełączenie nie wymaga ponownej ingestii).

### 3.2 Nowy plik: `backend/ecosim/core/workspace.py`

```python
@dataclass
class DataSource:
    id: str                    # stabilny slug, np. hash ścieżki + timestamp dodania
    name: str                  # nadana przez użytkownika etykieta, np. "Baltic Sea 2026-08"
    path: Path                 # folder źródłowy (odpowiednik dzisiejszego raw_dir)
    added_at: datetime
    last_scanned_at: datetime | None
    status: Literal["unscanned", "ok", "error"]
    error: str | None          # ostatni błąd ingestii, jeśli status == "error"

class WorkspaceRegistry:
    def list_sources(self) -> list[DataSource]: ...
    def add_source(self, name: str, path: Path) -> DataSource: ...
    def remove_source(self, source_id: str) -> None: ...   # zapomina, NIE kasuje danych źródłowych
    def set_active(self, source_id: str) -> None: ...
    def active(self) -> DataSource | None: ...
    def mark_scanned(self, source_id: str, *, ok: bool, error: str | None = None) -> None: ...
```

Trwałość: mały plik JSON **poza** jakimkolwiek katalogiem źródłowym danych — np.
`~/.ecosim/workspaces.json` (nowa, stała zmienna `ECOSIM_CONFIG_DIR`, domyślnie katalog
domowy użytkownika systemowego). To jedyny kawałek konfiguracji, który zostaje "na sztywno
przy starcie" — i tak musi gdzieś być zapisane "które źródła w ogóle znam".

### 3.3 Namespacing kanonicznego magazynu per źródło

Dziś `store_dir` (Parquet, DuckDB, zmaterializowane COG-i) jest jeden, wspólny. Przy wielu
źródłach **musi** być rozdzielony — inaczej przełączenie źródła pokazywałoby dane z
poprzedniego (albo, gorzej, mieszankę obu przez zbuforowane COG-i rastrów). Rozwiązanie:
`store_dir = <base_store_dir>/sources/<source_id>/`. To naturalne rozszerzenie już przyjętej
zasady **"index-fast, materialize-lazily"** (patrz pamięć projektu
[[ecosim-spatial-lazy-materialize]]) — zmaterializowane COG-i są tanie do odtworzenia, więc
przełączenie na nieaktywne od dawna źródło co najwyżej odtwarza cache leniwie, nie od zera.

### 3.4 Przebudowa `get_settings()`

```python
def get_settings() -> Settings:
    registry = get_workspace_registry()
    active = registry.active()
    if active is None:
        raise NoActiveDataSourceError(...)   # API zwraca 409, frontend przekierowuje na ekran wyboru źródła
    return Settings(raw_dir=active.path, store_dir=BASE_STORE_DIR / "sources" / active.id)
```

`@lru_cache` znika (albo zamienia się na cache kluczowany `active.id`, unieważniany przy
`set_active`/`add_source`) — konstrukcja `Settings` to tylko sklejanie ścieżek, więc brak
cache'a nic nie kosztuje. **Żadna inna funkcja w backendzie nie wymaga zmian** — patrz 1.

## 4. Nowe/zmienione API

| Endpoint | Opis |
|---|---|
| `GET /admin/sources` | lista znanych źródeł: id, name, path, status, last_scanned_at, który jest aktywny |
| `POST /admin/sources` `{name, path}` | rejestruje nowe źródło; szybka walidacja "czy to w ogóle wygląda jak eksport EwE" (patrz 4.1) — **nie** uruchamia jeszcze pełnej ingestii |
| `POST /admin/sources/{id}/activate` | ustawia jako aktywne + uruchamia pełną ingestię do jego namespaced store (reużywa istniejące `run_ingest`, `build_raster_index`, `build_catalog` — bez zmian w tych funkcjach) |
| `DELETE /admin/sources/{id}` | zapomina źródło (rejestr + jego cache w `store_dir`); **nigdy nie dotyka** oryginalnego folderu z danymi |
| `GET /admin/browse?path=` | ograniczone przeglądanie katalogów po stronie serwera (patrz 4.2) — zasila UI folder-pickera |
| `POST /admin/reload` | zostaje, ale teraz = ponowna aktywacja **aktualnie aktywnego** źródła (alias na `/admin/sources/{active_id}/activate`) |

### 4.1 Szybka walidacja przy rejestracji

Zanim cokolwiek się zaingestuje: sprawdzić, że folder istnieje, jest czytelny, niepusty, i
zawiera przynajmniej jedną rozpoznawalną poszlakę eksportu EwE (`Mapa_grupy_fleets.xlsx`,
albo plik `*_annual.csv`/`*_monthly.csv`, albo folder `output/`/`input/`) — czytelny błąd z
konkretną listą czego brakuje, **zero zgadywania**, ta sama filozofia co reszta projektu
([[ecosim-verify-against-ewe-docs]] stosuje się też tutaj: nie zakładamy, że folder jest
poprawny, tylko sprawdzamy). Pełna walidacja i tak następuje przy `activate` (ingestia sama
zgłosi błędy per plik, jak dziś).

### 4.2 `GET /admin/browse` — bezpieczeństwo

Frontend nie może "przeglądać systemu plików" przez API przeglądarki (to nie desktop-owa
apka) — folder-picker w UI musi więc pytać **backend**, co widzi. To rodzi realne pytanie
bezpieczeństwa na serwerze wieloosobowym: bez ograniczenia, dowolny użytkownik mógłby
przez ten endpoint przejrzeć cały system plików serwera. Na start: nowa zmienna
`ECOSIM_BROWSE_ROOT` (opcjonalna) ogranicza przeglądanie do jednego, skonfigurowanego przez
administratora katalogu bazowego (np. zamontowanego share'a); jeśli nieustawiona — tryb
lokalny/dev, przeglądanie bez ograniczeń (jak dziś, gdzie i tak tylko jedna osoba ma dostęp
do maszyny). **Pełna izolacja per użytkownik to Etap 4** (patrz sekcja 6) — dziś nie mamy
jeszcze auth, więc nie ma jeszcze "czyjego" folderu do chronienia przed kim innym.

## 5. Frontend

### 5.1 Nowy ekran: wybór/zarządzanie źródłem danych

Nowy komponent (`frontend/src/features/datasource/DataSourcePanel.tsx`):
- Lista znanych źródeł: nazwa, ścieżka, status (pill: ok/error/nieprzeskanowane), przyciski
  "Aktywuj" / "Przeskanuj ponownie" / "Zapomnij".
- "+ Dodaj źródło": pole tekstowe na ścieżkę (dla power-userów, wklejenie pełnej ścieżki) +
  przeglądarka folderów typu breadcrumb (odpytuje `GET /admin/browse`, klikalne wejście w
  podfoldery) + nazwa + przycisk "Dodaj i zeskanuj".
- Podczas aktywacji: prosty spinner/status (ingestia dziś jest synchroniczna — patrz 6) w
  tym samym stylu, co dzisiejszy komunikat `reloadMsg` w `App.tsx`.

### 5.2 Kiedy ten ekran się pokazuje

- **Zawsze, gdy `GET /admin/sources` nie ma aktywnego źródła** (świeża instalacja, albo
  źródło zostało zapomniane) — blokująco, przed `Landing.tsx`, dokładnie jak prosił
  użytkownik: "już na pierwszym ekranie".
- **Na żądanie w każdej chwili** — górny pasek (`App.tsx`) dostaje kontrolkę "Źródło danych:
  `<nazwa>` ▾" w miejscu dzisiejszego samego przycisku "Reload Data" (który zostaje jako
  szybka akcja "odśwież bieżące źródło" wewnątrz tej kontrolki).

### 5.3 Migracja — nie zgubić dzisiejszych danych

Przy pierwszym uruchomieniu po tej zmianie: jeśli `<project_root>/DataEcosim` istnieje na
dysku, automatycznie zarejestrować je jako źródło (np. nazwa "DataEcosim (domyślne)") i
ustawić jako aktywne — dotychczasowi użytkownicy/deweloperzy nie tracą dostępu do danych i
nie muszą nic ręcznie wskazywać, żeby wrócić do stanu sprzed zmiany.

## 8. Pytania otwarte do użytkownika

1. **Czy "share" to zamontowany katalog sieciowy widoczny w systemie plików serwera** (SMB/
   NFS/dysk sieciowy — założenie tego planu), **czy jednak potrzebny jest prawdziwy upload
   przez przeglądarkę** (np. dla mniejszych, pojedynczych aktualizacji bez dostępu do
   samego share'a)? Zmienia to architekturę: upload HTTP dla ~28 GB wymagałby osobnej,
   znacznie cięższej funkcji (przesył kawałkami, wznawianie, limit miejsca) — nieplanowanej
   w tym dokumencie.
2. **Czy share ma być jednym wspólnym katalogiem z podfolderami per projekt/użytkownik**
   (np. `/mnt/ewe-share/<projekt>/`), czy każdy użytkownik dostaje osobny, odizolowany
   punkt montowania? Wpływa na to, jak bardzo pilne jest ograniczenie `ECOSIM_BROWSE_ROOT`
   z sekcji 4.2 i na kształt Fazy 3.
3. **Czy w Fazie 1 wystarczy jedno aktywne źródło na całą instancję aplikacji** (tak jak
   dziś, tylko przełączalne), czy od razu potrzebne jest równoległe przeglądanie kilku
   źródeł naraz przez różne osoby na tym samym serwerze? To druga rzecz spycha projekt
   prosto w stronę Fazy 3 (auth) już teraz, zamiast poczekać na realną potrzebę.
