1. **porządkuje i indeksuje** surowe dane EwE tak, by dało się po nich nawigować,

## 2. Co zastałem w danych (`DataEcosim/`, ~14 tys. plików)

Model EwE Bałtyku, **50 grup funkcyjnych**, **9 flot**, lata **1998–2050**, krok
miesięczny i roczny.

- **`output/<scenariusz>_cumulative/`** — wyniki:
  - `ecosim_<run>/` — CSV szeregów czasowych w **trzech formatach** (szeroki
    `rok×grupa`, długi `year,fleet,group,value`, jednoseryjny) + per-grupa
    `predation_*` (szeroki wg nazw drapieżników). Każdy plik z **blokiem nagłówka
    metadanych** (EwEVersion, ModelName, StartYear, EcosimScenario).
  - `asc/` — ~13,6 tys. map przestrzennych `EcospaceMapBiomass-<grupa>-<krok>.asc`
    (siatka ESRI ASCII 675×374, WGS84) + `Ecospace RunInfo.txt` (geo-metadane).
- **`input/<scenariusz>/`** — drivery: baza `.eweaccdb`, XML scenariusza (mapuje
  zmienną → roczne mapy `.asc`), foldery driverów (PP, Bottom O2, Salinity, Temp,
  CodRV...) z rocznymi `.asc` + `trend_<scenariusz>.csv` (średnia przestrzenna jako
  szereg czasowy).
- **`Mapa_grupy_fleets.xlsx`** — słownik kodów ↔ nazw grup i flot (kluczowy: format
  szeroki używa ID `1..50`, predacja używa nazw).

## 3. Architektura: „surowe → kanoniczne → prezentacja"

Kluczowa zasada: **nikt powyżej warstwy ingestii nie czyta surowego `DataEcosim/`.**
Pipeline raz parsuje cały bałagan do kanonicznego tidy store, a API, frontend i
skrypty R pracują wyłącznie na tym modelu. To fundament modularności i sens
„domyślnego formatu" dla R.

```
DataEcosim/ (surowe, niezmienne)
   │  INGESTIA (Python): rejestr parserów → tidy
   ▼
Kanoniczny STORE              KATALOG (DuckDB) — indeks do nawigacji
  • timeseries/ (Parquet)  ◄────────────┘
  • spatial/ (COG + indeks)  [Etap 2]
  • dictionaries/ (groups, fleets, scenarios)
   │
   ├─► API (FastAPI): /catalog, /timeseries, /spatial, /analyses, /jobs
   │      └─► Frontend (React): katalog, wykresy, mapy, runner analiz
   └─► R RUNNER: sandbox plikowy (manifest + data) → Rscript → out/result.json
```

### Kanoniczny schemat szeregów czasowych (tidy)
Wszystkie formaty sprowadzone do jednej tabeli:
`scenario, domain, variable, freq, date, year, month, group_id, group_name,
fleet_id, fleet_name, partner_id, partner_name, value, unit`
(`partner_*` = grupa interagująca, np. drapieżnik w predacji).

### Cztery punkty rozszerzalności (modularność)
1. **Rejestr parserów** — nowy typ pliku = nowy parser w `ingestion/parsers/`.
2. **Dyspatch po kształcie nagłówka** (nie po nazwie pliku) — odporny na warianty.
3. **Pluginy analiz R** — folder `rkit/analyses/<id>/` z `analysis.yaml` + `entry.R`.
4. **Renderery wyników w UI** — dobierane po `type` artefaktu z `result.json`.

## 4. Kontrakt R (domyślny format dla naukowców)

Skrypt dostaje gotowy sandbox i zwraca ustrukturyzowane wyniki — nigdy nie zna
struktury `DataEcosim/`. Pełna specyfikacja: `docs/data-contract.md`.

```
job_<id>/
  manifest.json     # selekcja z UI: scenariusze, zmienne, grupy, zakres lat, freq
  params.json       # parametry formularza danej analizy
  data/
    timeseries.parquet   # JUŻ przefiltrowane wg selekcji (schemat tidy)
    spatial/             # (analizy przestrzenne) COG + raster_index.csv
    dictionaries/        # groups.csv, fleets.csv, scenarios.csv
  out/              # <-- skrypt zapisuje wyniki + result.json
```

`out/result.json` opisuje artefakty z polem `type` (`figure|table|map|scalar|
vega_spec`), po którym frontend dobiera renderer. SDK **`ecosimkit`** (R) udostępnia
`ecosim_load_timeseries()`, `ecosim_params()`, `ecosim_dict()` oraz emitery
`ecosim_emit_figure/table/map/scalar()` — naukowiec nie pisze boilerplate'u.

Uruchamianie: lokalnie `Rscript entry.R`; na serwerze identycznie, ale w kontenerze
za kolejką zadań — **kontrakt bez zmian** (sandbox plikowy, język-agnostyczny).

## 6. Co zostało zrobione i jak (Etap 0 + Etap 1) — ZWERYFIKOWANE

### Zaimplementowane
- **Parser CSV** (`ingestion/parsers/ecosim_csv.py`) — obsługuje wszystkie 4 kształty,
  dyspatch po nagłówku sekcji `Data`, parsuje blok metadanych, zamienia miesięczne
  timestepy na daty (StartYear + offset). Zwektoryzowany (`melt`/`map` w pandas).
- **Słownik** (`group_map.py`) — `Mapa_grupy_fleets.xlsx` → 50 grup + 9 flot,
  mapowanie ID↔nazwa (także rozwiązywanie nazw z różną wielkością liter).
- **Trendy driverów** (`trend_csv.py`) — `trend_*.csv` → tidy (domain=input).
- **Zapis Parquet** (`store.py`) — partycje `scenario=/domain=/variable=/freq=`,
  stabilny schemat Arrow.
- **Pipeline** (`pipeline.py`) — odkrywanie scenariuszy, ingestia per-scenariusz
  (zapis i zwolnienie pamięci), eksport słowników, przebudowa katalogu.
- **Katalog DuckDB** (`catalog/build.py`, `service.py`) — tabela datasetów + wymiary
  + widok `timeseries` nad Parquet; zapytania read-only dla API.
- **API FastAPI** — `/health`, `/catalog/scenarios|tree|datasets`,
  `/dictionaries/groups|fleets`, `/timeseries` (filtry: scenariusze, grupy, floty,
  zakres lat).
- **CLI** — `python -m ecosim.cli ingest|catalog|serve`.
- **Testy** — 6 testów parsera na realnych próbkach.

### Wynik weryfikacji E2E
- Ingestia: **668 plików → 7 828 789 wierszy, 410 datasetów, 5 scenariuszy** w ~60 s.
- Scenariusze: `baltic_ecosim`, `baseline_cumulative`, `has_cumulative` (output) +
  `bau`, `has` (input).
- Zapytanie `biomass / Cod adult / 2 scenariusze / 1998–2000` zwraca poprawnie 6 serii.
- `pytest`: 6/6 passed.

### Problemy napotkane i naprawione
1. **TLS/instalacja** — `pip` w tym venv ma zepsuty OpenSSL; firmowy CA. Rozwiązanie:
   `uv pip install --native-tls` (certyfikaty systemowe Windows). pandas==3.0.3.
2. **Wydajność** — pierwotne pętle wierszowe w Pythonie były zbyt wolne (>6 min,
   przerwane). Zwektoryzowano na `melt` (63 s).
3. **Tożsamość scenariusza (ważne!)** — `output/Baseline_cumulative/` zawiera **dwa
   różne runy Ecosim** (`ecosim_Baltic_Ecosim` i `ecosim_baseline cumulative`,
   różne `EcosimScenario`), które początkowo zlewały się w jeden scenariusz
   (duplikaty wartości). Poprawka: id scenariusza pochodzi z nazwy katalogu runu
   `ecosim_<run>`, nie z folderu nadrzędnego.

## 8. Szybki start (tryb lokalny)

```powershell
# Instalacja zależności (uv + native-tls przez firmowy CA)
$env:VIRTUAL_ENV = (Resolve-Path .\.venv).Path
uv pip install --native-tls -e .\backend[dev]

# Ingestia surowych danych → kanoniczny store + katalog
$env:PYTHONPATH = "backend"
python -m ecosim.cli ingest

# Serwer API (http://127.0.0.1:8000/docs)
python -m ecosim.cli serve --reload
```

Przykładowe zapytania:
```
GET /catalog/tree
GET /timeseries?variable=biomass&freq=annual&scenario=baseline_cumulative&scenario=has_cumulative&group=Cod%20adult
```
